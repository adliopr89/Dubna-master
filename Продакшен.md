# Мастера Дубны — вывод в продакшен (свой сервер + PostgreSQL)

План того, что нужно сделать, когда поднимаем проект на своём сервере.
Целевая схема:

```
Telegram ──► @DubnaMaster_bot (webhook)
                    │
Пользователи ──► https://домен/  (Caddy/nginx → Node)
                    ├─ /          → статика Mini App
                    ├─ /api/*     → REST-эндпоинты
                    └─ бот        → webhook или long-poll
                          │
                    PostgreSQL (тот же сервер)
```

---

## 1. Что доработать в коде

### 1.1 Слой данных → PostgreSQL
Сейчас весь стейт — один объект `DB` + `GET/PUT /api/state`. Заменить на:

- `app/server/pg.js` — пул `pg` + миграции (`migrations/001_init.sql`).
- Таблицы (по «Схеме данных» с доски):
  - `masters(id, code UNIQUE, name, spec, phone, tg, tg_id, tz, horizon, ttl_h, ttl_m, step, cancel_h)`
  - `master_days(master_id, date, from_t, to_t, PRIMARY KEY(master_id, date))`
  - `master_breaks(day_id | master_id, date, from_t, to_t)` — или jsonb-колонка `breaks` в `master_days`
  - `clients(id, name, phone, tg, tg_id UNIQUE, rem jsonb)`
  - `links(id, client_id, master_id, status, comment, label, UNIQUE(client_id, master_id))`
  - `requests(id, client_id, master_id, date, svc, wish, status)`
  - `offers(id, request_id, start_ts, dur_min, until_ts, status)` — UNIQUE на пересечение интервалов реализовать в транзакции
  - `notes(id, to_id, text, ts, seen, sent)`
- Ключевая транзакция: **выбор времени клиентом** — `SELECT ... FOR UPDATE` записей мастера на день → проверка пересечения интервала → INSERT. Это закрывает двойное бронирование.
- Индексы: `offs(request_id)`, `offs(start_ts)`, `links(client_id)`, `links(master_id)`, `notes(to_id, seen)`, `master_days(master_id, date)`.

### 1.2 REST-эндпоинты (вместо PUT-всего-стейта)
```
GET  /api/me                     — кто я (по initData) + мои связи
GET  /api/masters/:id/avail      — рабочие дни + свободные интервалы
POST /api/links                  — заявка на присоединение (код/ссылка + комментарий)
POST /api/links/:id/answer       — принять/отклонить (мастер)
POST /api/reqs                   — заявка на запись
POST /api/reqs/:id/offers        — мастер предлагает время(а)
POST /api/offs/:id/pick          — клиент выбирает вариант (транзакция!)
POST /api/reqs/:id/cancel        — отмена (клиент/мастер, комментарий)
POST /api/masters/:id/cancel-range — отмена за период
POST /api/masters/:id/days       — рабочий день + перерывы
DELETE /api/masters/:id/days/:d
POST /api/masters/:id/bookings   — ручная запись (вне бота)
GET  /api/notes                  — лента уведомлений
PUT  /api/clients/:id/rem        — настройки напоминаний
PUT  /api/masters/:id/settings   — горизонт/жизнь брони/шаг/лимит отмены
```
В webapp: 15–20 функций-действий (`sendReq`, `sendOffer`, `pickOffer`, `cancelOne`,
`addBook`, `saveBook`, `addWorkDay`, `addBreak`, `setRem`...) мапятся на эндпоинты.
Рендер и логика `free()`/интервалов остаются. Отказаться от «весь стейт в памяти»:
экраны грузят свои данные запросами + локальный кэш.

### 1.3 Бот
- Оставить Node long-poll (работает и без webhook) **или** webhook на тот же домен:
  `setWebhook https://домен/tg/<secret>` — лучше: меньше latency, события мгновенно.
- Уведомления и заявки с кнопками — как сейчас, но читают/пишут PG.

## 2. Безопасность — обязательный чек-лист

### Аутентификация
- [ ] **Проверка `initData` Telegram WebApp**: HMAC-SHA256(`secret_key=HMAC("WebAppData", bot_token)`) — обязательно. Сейчас вообще нет auth — любой PUT-ит что угодно. Выпускать короткоживущий JWT после проверки, или валидировать подпись на каждый запрос (`Authorization: tma <initData>`).
- [ ] **Авторизация по ролям**: каждый эндпоинт проверяет, что `me` — участник связи (клиент не читает чужие записи, мастер — только своих клиентов).
- [ ] Мастера заводит админ (`ADMIN_TG`) — саморегистрации мастера нет.

### API / входные данные
- [ ] Параметризованные запросы только (`$1,$2`) — защита от SQL-инъекций.
- [ ] Валидация входа: длина полей (svc ≤ 500, комментарий ≤ 1000), даты не в прошлом,
  время внутри рабочего дня, `dur` кратна `step`, коды только `\d{4}`.
- [ ] Rate limiting на эндпоинтах записи (напр. 30 req/min/IP) — express-rate-limit или самописный.
- [ ] Никакого `eval`/innerHTML с пользовательским текстом — уже `esc()`, проверить новые места.

### Транспорт и секреты
- [ ] HTTPS обязателен (Caddy авто-Let’s Encrypt). HSTS.
- [ ] `BOT_TOKEN` — только env/secret-файл вне репо (уже в .gitignore).
- [ ] CORS: whitelist `https://adliopr89.github.io` + свой домен (если webapp на Pages отдельно).
- [ ] Webhook: `X-Telegram-Bot-Api-Secret-Token` проверка.

### Данные и приватность
- [ ] Телефоны/tg_id — персональные данные: минимум в логах, доступ только владельцу/мастеру.
- [ ] Бэкап PG: `pg_dump` по cron раз в сутки, хранить 7–14 дней (отдельная папка/бакет).
- [ ] Логи без содержимого initData и текстов сообщений.

### Сервер
- [ ] Доступ по SSH только по ключам, root-логин выключен, fail2ban.
- [ ] UFW: открыты 22, 80, 443; PG слушает только localhost.
- [ ] Node-процесс под systemd (Restart=always), отдельный непривилегированный юзер.
- [ ] Регулярные `apt update && apt upgrade` (unattended-upgrades).

## 3. Требования к серверу

Нагрузка мизерная (десятки пользователей → сотни в перспективе): достаточно минимума.

| Ресурс | Минимум | Комфорт |
|---|---|---|
| CPU | 1 vCPU | 2 vCPU |
| RAM | **1 ГБ** (Node ~120 МБ + PG ~150–300 МБ) | 2 ГБ |
| Диск | 10 ГБ SSD | 20 ГБ |
| OS | Ubuntu 22.04/24.04 | та же |
| Сеть | белый IP + домен | то же |

### Бесплатные варианты (честно)

- **Oracle Cloud Always Free** — лучший «бесплатный навсегда»: ARM VM до 4 cores / 24 ГБ RAM / 200 ГБ. Запас с огромным запасом. Минус: регистрация с картой, ARM-архитектура (Node/PG ставятся без проблем).
- **Fly.io** — free allowance (маленькая VM), спит при бездействии если не настроить; volume под PG платный/ограничен.
- **Render free** — засыпает (первый запрос ~30–60 с) → бот/напоминания сломаются. Не годится для фоновых задач без крон-пинга.
- **Railway** — trial-кредиты, потом платно.
- **Свой ПК/RPi + белый IP или Cloudflare Tunnel** — тоже вариант, но туннели из РФ у тебя уже рвались (см. AGENTS «Онлайн тренер»).

**Рекомендация**: Oracle Always Free или любой дешёвый VPS (~150–300 ₽/мес — Timeweb/Selectel/Yandex Compute micro). Платный микро-VPS честнее «бесплатных».

### Стек на сервере
```
Ubuntu 24.04 + Node 24 + PostgreSQL 16 (localhost) + Caddy (HTTPS) + systemd unit
Домен: свой или бесплатный duckdns.org → Caddy сам выпустит сертификат.
```

## 4. Порядок работ при деплое

1. Поднять PG + миграции (`pg.js`, `001_init.sql`), сид мастеров.
2. Переписать сервер на REST-эндпоинты (п. 1.2) + auth по initData.
3. Переключить webapp: `API_URL` константа → свой домен, экшены → fetch-эндпоинты.
4. Бот → webhook `https://домен/tg/<secret>` (или оставить long-poll на старте).
5. Caddy reverse-proxy → Node, HTTPS, BotFather `setChatMenuButton`/`setWebhook`.
6. Нагрузочный прогон: 2 персоны одновременно бронируют одно время → гонки нет.
7. Бэкапы pg_dump по cron + мониторинг (healthcheck /api/health).

## 5. Что останется «на потом»

- Админ-экран заведения мастеров (сейчас сид/SQL).
- Оплата/абонемент мастеров (если будет монетизация).
- Мультиязычность, роли-помощники у мастера, выгрузка отчётов.
